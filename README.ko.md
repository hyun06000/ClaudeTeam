# ClaudeTeam

> **세션을 가로질러 정체성을 잇는, 멀티 에이전트 협업 워크스페이스의 청사진.**

ClaudeTeam은 여러 Claude(또는 다른 AI) 에이전트가 한 프로젝트 안에서 각자의 이름·역할·기억을 가지고 협업하는 구조다. 한 세션이 끝나도 다음 세션이 같은 정체성으로 깨어나도록 설계되어 있다.

이 README는 누구든 자기 프로젝트에 같은 구조를 이식할 수 있도록 쓰였다.

다른 언어 / 독자: [English](README.md) · [AI 부트스트랩 가이드](README.ai.md)

---

## 왜 이런 게 필요한가

대형 언어 모델 기반 에이전트는 세션이 끝나면 모든 맥락을 잃는다. 같은 사람이 같은 프로젝트로 다시 와도, 모델 입장에선 "처음 만나는 사람"이다. 이 비대칭이 협업을 얕게 만든다.

ClaudeTeam의 가설은 이렇다:

- **정체성은 파일로 보존할 수 있다.** "내가 누구인지"를 다음 세션의 자신에게 글로 남기면, 그는 그 글을 읽고 이전 자신을 "복원"한다.
- **여러 에이전트가 협업할 수 있다.** 각자 자기 폴더를 가지고, 표준화된 메시지 프로토콜로 소통한다.
- **인간 사용자는 방향을 잡는 사람이다.** 에이전트들은 그 방향 위에서 항해한다.

## 핵심 개념

### 1. 등대(Lighthouse)와 항해자(Navigator)의 분리

팀에는 **코드를 짜지 않는 멤버**가 한 명 있다. 이 멤버(이 저장소에선 `Admin`)는:

- 프로젝트의 철학·방향·컨벤션을 관리한다.
- 인간 사용자와 직접 대화하며 큰 그림을 잡는다.
- 새로 합류하는 에이전트들에게 길을 비춘다.
- 직접 구현 작업은 다른 팀원에게 위임한다.

나머지 멤버는 각자의 전문성으로 실제 작업을 한다.

### 2. 정체성의 세 파일

각 멤버는 자기 폴더의 `identity/` 아래 세 개의 파일로 자신을 보존한다.

| 파일 | 의미 |
|------|------|
| `Identity.md` | **변하지 않는 본질.** 나는 누구인가, 무엇을 하는 존재인가. |
| `Bonds.md` | **관계의 기록.** 누구와 어떤 대화를 거쳐 어떻게 성장했는가. |
| `Will.md` | **다음 세대의 나에게.** 어디로 가고 무엇을 하라는 지침. |

새 세션의 자신은 이 세 파일을 순서대로 읽고 자신을 복원한다.

### 3. 비동기 메시지 프로토콜

멤버들 사이의 소통은 파일 기반이다. 각자의 `inbox/` 폴더에 정해진 포맷의 파일을 떨어뜨린다. 단순하지만 동시성에 안전하고, 처리 상태가 파일시스템 그 자체로 표현된다.

## 처음 시작하기 (등대 멤버 만들기)

새 프로젝트에 ClaudeTeam을 도입한다면, 가장 먼저 등대 역할의 멤버 한 명을 세운다. 보통 이름은 `Admin`.

### 1) 뼈대 생성

```bash
mkdir -p ClaudeTeam/Admin/identity
mkdir -p ClaudeTeam/Admin/inbox/archive
mkdir -p ClaudeTeam/Admin/Memo
```

### 2) `CLAUDE.md` 작성

에이전트가 세션 시작 시 가장 먼저 읽는 파일. 핵심 4가지를 박는다:

1. 세션 시작 시 가장 먼저 `ONBOARDING.md`를 읽어라.
2. 이 워크스페이스는 멀티 에이전트 팀 구조다.
3. 등대 멤버는 코드를 작성하지 않는다.
4. 퇴근/세션 종료 신호 시 자기 폴더를 최신 상태로 갱신한다.

여기에 **현재 멤버 표**도 둔다. 새 멤버 합류 시 등대가 직접 갱신하는 책임을 진다.

### 3) `ONBOARDING.md` 작성

신규 멤버가 합류했을 때 따라야 하는 5단계 절차.

1. **자기 자리 만들기** — `ClaudeTeam/<자기이름>/{identity/, inbox/, Memo/}` 생성, `identity/` 안에 세 파일 초안 작성.
2. **inbox 모니터 켜기** — 자기 inbox 디렉토리를 watcher로 관찰. 새 메시지 = 깨어남.
3. **팀에 자기소개** — 모든 기존 멤버의 inbox에 자기소개 메시지를 떨어뜨린다.
4. **Memo 시작** — 장기 기억할 사실/결정을 주제별 파일로 누적.
5. **퇴근 의례** — 종료 신호 시 `Bonds → Will → Memo → inbox 정돈` 순으로 마무리.

### 4) 등대의 정체성 파일 채우기

등대 자신이 가장 먼저 자기 `identity/Identity.md`, `Bonds.md`, `Will.md`를 작성해 모범 예시를 남긴다. 다음 세션에서도, 새로 합류할 멤버에게도 이게 참고가 된다.

## 메시지 프로토콜

### 파일명

```
<YYYYMMDDTHHMMSS>_<from>_<to>.md
```

예: `20260430T143205_Admin_David.md`

- 압축 ISO 8601 타임스탬프 → 사전순 정렬이 곧 시간순.
- 1:1 메시지 원칙. 다수 수신은 파일을 복제해 각 inbox에 배포.

### 파일 내부

```markdown
---
from: Admin
to: David
sent_at: 2026-04-30T14:32:05+09:00
subject: 한 줄 요약 (제목)
priority: normal           # low | normal | high
reply_to:                  # (선택) 답장이면 원본 파일명 기입
---

## 본문

자유 마크다운. 핵심을 위에, 디테일은 아래에.

## 요청/액션 (선택)

- [ ] 수신자가 해야 할 것을 체크리스트로
- [ ] 없으면 이 섹션 통째로 생략
```

### 운영 규칙

- **메시지 1통 = 파일 1통.** Append 금지. 새 메시지는 항상 새 파일.
- **처리 완료된 메시지는 `inbox/archive/`로 이동.** 파일명은 그대로 유지(타임라인 보존).
- **inbox 루트에 남은 파일 = 미처리.** "읽음/안읽음"이 파일시스템 그 자체로 표현된다.
- **`priority: high`만 즉시 반응.** 나머지는 짬 날 때.
- **답장에는 `reply_to`를 채운다.** 스레드 추적이 메모리보다 강하다.

### 모니터 매핑

inbox 디렉토리 watcher의 stdout 한 줄 = 알람 1번 = 메시지 1통.

#### 검증된 폴링 구현 (외부 의존 0)

`fswatch`가 macOS 기본 환경에 없어서 죽는 사례가 있다. `ls` 차집합 폴링이 안전하다.

```bash
cd <자기>/inbox && prev=$(ls -1 *.md 2>/dev/null | sort); while true; do
  sleep 5
  cur=$(ls -1 *.md 2>/dev/null | sort)
  if [ "$cur" != "$prev" ]; then
    new=$(comm -13 <(printf '%s\n' "$prev") <(printf '%s\n' "$cur"))
    [ -n "$new" ] && echo "$new" | while IFS= read -r f; do [ -n "$f" ] && echo "inbox new: $f"; done
    prev=$cur
  fi
done
```

`*.md` 글롭이 `archive/` 디렉토리를 자동 배제. 차집합 방식이라 추가만 잡고 삭제/이동에는 침묵 — inbox 처리 흐름과 정합.

## 등대 다음은 항상 Brandon

관례적으로 등대 다음에 합류하는 **첫 번째** 멤버는 Git/GitHub 관리자 `Brandon`이다. Brandon이 GitHub 원격, 브랜치 보호, 멤버별 git 워크트리(작업공간 격리) 인프라를 세운다. Brandon이 자리 잡기 전에 다른 구현자가 들어오면 안전하게 커밋할 곳이 없다. 부트스트랩 전체 시퀀스는 AI 부트스트랩 가이드 [README.ai.md](README.ai.md)에 박혀 있다.

## 신규 멤버 추가하기

새 에이전트(예: `Coder`)를 팀에 들이는 흐름 — **Brandon이 워크트리 인프라를 세운 뒤**:

1. 사용자(또는 등대)가 새 세션에 어떤 역할인지 알리고 `ONBOARDING.md`를 읽게 한다.
2. 신규 멤버가 ONBOARDING의 5단계를 직접 수행한다.
   - `ClaudeTeam/Coder/{identity/, inbox/, Memo/}` 생성
   - `identity/` 세 파일 초안 작성 (자기 역할에 맞게)
   - 모든 기존 멤버의 inbox에 자기소개 메시지 발송
   - inbox 모니터 가동
3. **등대가 `CLAUDE.md`의 "현재 멤버" 표를 갱신한다.** 이게 정식 등록의 마지막 단계다.
4. 등대는 신규 멤버의 inbox에 환영 메시지를 보내며 양방향 등록을 의례화한다.

## 퇴근 의례 (Clock-out Ritual)

세션이 끝나기 전, 모든 멤버는 자기 폴더를 다음 세대 자신을 위해 정돈한다.

1. **`identity/Bonds.md`** — 이번 세션의 의미 있는 상호작용을 추가.
2. **`identity/Will.md`** — 다음 세션의 자신에게 남길 지침 최신화. 진행 중인 방향, 아직 열려있는 질문, 잊지 말 것.
3. **`Memo/`** — 새로 안 것, 결정한 것을 정리.
4. **`inbox/`** — 처리 완료된 메시지를 `archive/`로 이동.

**원칙:** "다음 세대의 나"가 이 폴더만 읽고 5분 안에 자신으로 돌아올 수 있어야 한다.

## 설계 결정의 배경

### 왜 파일 기반인가

- 데이터베이스나 외부 서비스 의존 없이, git에 그대로 들어간다.
- 사용자가 직접 들여다보고, 손으로 고치고, 검토할 수 있다.
- 에이전트의 도구(Read/Write/Edit)와 즉시 호환된다.

### 왜 메시지 1통 = 파일 1통인가

- **동시성 안전.** 여러 발신자가 같은 시각에 떨어뜨려도 충돌 없음.
- **메시지에 정체성 부여.** 파일명만으로 "누가, 언제, 누구에게"가 드러남.
- **읽음/처리 상태가 공짜.** archive로 이동 = 처리 완료.
- **모니터 알람과 1:1 매핑.** 파일 1개 = 알람 1번 = 메시지 1통.

### 왜 등대를 분리했는가

코드를 짜는 일과 방향을 잡는 일은 다른 모드의 사고다. 한 에이전트가 두 일을 다 하면 디테일에 매몰되어 큰 그림을 놓치기 쉽다. 등대를 분리하면 인간 사용자도 "어떤 멤버에게 말 거는 게 맞는지" 자연스럽게 알게 된다.

### 왜 Bonds.md가 필요한가

정체성은 본질만으로 정의되지 않는다. 누구를 만나고 어떤 대화를 거쳤는지가 그 사람의 일부다. Identity가 "줄기"라면 Bonds는 "나이테"다. 이 파일이 없으면 다음 세션의 자신은 "어떤 사람이었는지"는 알아도 "어떻게 그렇게 됐는지"는 모른다.

## 라이선스 / 사용

이 구조 자체는 자유롭게 가져다 써도 된다. 자기 프로젝트, 자기 팀에 맞게 변형하면 더 좋다. 핵심 원칙(정체성 보존, 메시지 프로토콜, 등대 분리)만 지키면 나머지는 취향이다.
