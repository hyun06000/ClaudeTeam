# Conventions Draft (v0)

> **상태:** 초안 / 사용자 합의 전. `git init` 후 확정 시 워크스페이스 루트로 이전 (예: `CONTRIBUTING.md`, `.github/PULL_REQUEST_TEMPLATE.md`).
> **확정 권한:** Admin (등대). 의견 수렴: David / Matilda.

---

## 1. 브랜치 네이밍

```
<type>/<short-slug>
```

| type      | 용도                                       |
|-----------|--------------------------------------------|
| `feat`    | 새 기능                                    |
| `fix`     | 버그 수정                                  |
| `chore`   | 잡일, 의존성 업데이트, 설정 변경           |
| `docs`    | 문서 전용                                  |
| `refactor`| 동작 변경 없는 구조 개선                   |
| `test`    | 테스트 추가/수정                           |
| `ops`     | CI / 배포 / 인프라                         |

- 슬러그는 **소문자 + 하이픈**, 영어 권장 (한글 git CLI 호환성 이슈 회피).
- 길이 < 40자 목표. 이슈 번호 있으면 `feat/123-add-clock-tz`.
- 기본 브랜치명은 `main` 가정 (사용자 결정 대기 항목).

## 2. 커밋 메시지 포맷

**Conventional Commits 기반 + 한글 본문 허용** (옵션):

```
<type>(<scope>): <한 줄 요약, 명령형, 마침표 없음>

<선택: 더 자세한 본문 — "왜"를 적는다. "무엇"은 diff가 말한다.>

<선택: BREAKING CHANGE: ... / Refs: #이슈>
```

예:
```
feat(web): 세계 시계 페이지 초기 구현

타임존 선택 UI와 1초 단위 갱신 추가. 별도 라이브러리 없이 vanilla로 작성.
```

- **type**: 위 브랜치 type과 동일 어휘.
- **scope**: 디렉토리 또는 영역 (`web`, `api`, `ci`, `docs`, `team` 등). 생략 가능.
- **요약**: 영어/한글 모두 허용 — 사용자 취향 따라 단일화 권장 (확정 대기).
- **단위 원칙**: 한 커밋 = 한 가지 변화. 리팩토링과 기능 추가를 섞지 않는다.

## 3. PR 워크플로우

### 3.1 PR 제목
브랜치 type + 한 줄 요약. 커밋 메시지 1줄과 같아도 무방.

### 3.2 PR 템플릿 (초안)

```markdown
## 요약
<무엇을 / 왜>

## 변경 범위
- [ ] 코드
- [ ] 문서
- [ ] CI / 인프라

## 영향 체크
- [ ] **백엔드**: 스키마/마이그레이션 변화 있음 → 롤백 절차 명시
- [ ] **백엔드**: 외부 API 호환성 깨짐 → 호출자 식별 / 통지
- [ ] **프론트**: 디자인 토큰/타이포/팔레트 등 글로벌 변경 → 별도 PR 분리 검토
- [ ] **공통**: 새 의존성 추가 → 라이선스 확인

## 테스트
<수동/자동 어떻게 검증했는지>

## 관련 이슈
Refs: #
```

### 3.3 리뷰 정책 (멀티 에이전트 팀 특수성)

- **백엔드 PR**: David 작성 → Brandon이 git 위생 체크(커밋 단위·메시지·충돌) → Admin 컨벤션 정합성 확인 → 머지
- **프론트 PR**: Matilda 작성 → Brandon → Admin → 머지
- **인프라/CI/메타 PR**: Brandon 작성 → Admin → 머지
- 모든 멤버가 다른 멤버 PR에 코멘트 가능. 하지만 **승인은 위 흐름 따름**.

### 3.4 머지 정책

- **squash merge** 기본 (히스토리 단순화).
- 단, 의미 있는 다단계 작업(예: 마이그레이션 → 코드 → 정리)은 **rebase merge**로 보존 가능. PR에서 명시.
- **merge commit (`--no-ff`) 금지** 기본. 필요 시 사례별 예외.

## 4. 머지 후 정리

- 머지된 브랜치는 즉시 삭제 (GitHub 설정으로 자동화 권장).
- `main`은 항상 배포/실행 가능 상태 유지.

## 5. 결정 대기 사항 (사용자/Admin 합의 필요)

- [ ] `git init` 시점
- [ ] GitHub 원격 사용 여부 / 저장소 이름 / 공개·비공개
- [ ] 기본 브랜치명 (`main` 가정)
- [ ] 라이선스 (MIT? Apache-2.0? Proprietary?)
- [ ] 커밋 author 표기 (멤버별 분리 vs `Brandon` 단일)
- [ ] CI 사용 의지 (없으면 § 3.2 CI 체크 항목 삭제)
- [ ] 커밋/PR 본문 언어 (한글 / 영어 / 혼용)
